# Dataset & synthetic ground truth

`archive/paysim.csv` is not in this repo (see [Reproducibility](#reproducibility)) --
this document covers where it comes from, why it's the right base for this
project, and how the actual ground truth this project evaluates against was
built on top of it.

## Source: PaySim

[PaySim](https://www.kaggle.com/datasets/ealaxi/paysim1) is a synthetic
mobile-money transaction dataset generated by simulation, calibrated against
real (anonymized, aggregated) transaction logs from an African mobile money
provider. It's a standard, publicly available Kaggle dataset -- 6,362,620
transactions, ~470MB as CSV.

Columns: `step` (1-hour time unit, 1-743), `type` (`PAYMENT`/`TRANSFER`/
`CASH_OUT`/`CASH_IN`/`DEBIT`), `amount`, `nameOrig`/`nameDest` (account ids,
`C`-prefixed for customer, `M`-prefixed for merchant), `oldbalanceOrg`/
`newbalanceOrig`/`oldbalanceDest`/`newbalanceDest`, `isFraud`,
`isFlaggedFraud`.

**Two Kaggle quirks, neither used as a label anywhere in this project:**

- `isFlaggedFraud` is a near-constant, low-signal hardcoded rule in the
  original simulation (16 positives out of 6.36M rows) -- not a real
  detector output.
- `isFraud` flags individual fraudulent *transactions*, not ring/collusion
  membership. A transaction can be `isFraud=1` with no other account
  involved, and a planted collusion ring here never sets it. Using it as
  ring ground truth would be a category error.

`src/data/load_paysim.py` loads both columns for reference only and
documents this explicitly; nothing downstream reads them.

## Why PaySim, not real data

It gives realistic transaction volume, type mix, and amount distributions
to plant synthetic rings into and detect them against, without touching any
real user or financial data -- the right base for a synthetic benchmark
where the interesting part is the ring-detection pipeline, not the
underlying transactions.

## How ground truth was built

PaySim itself has no collusion-ring labels, so `src/data/plant_rings.py`
manufactures them: it builds a directed transaction graph from the loaded
PaySim rows, then plants synthetic rings on top with `networkx`. This
planted structure -- not anything in the original CSV -- is the actual
ground truth `src/eval/metrics.py` scores against.

Three ring types, each planted at **obvious** and **subtle** difficulty (4
rings per type/difficulty combo, 3-6 members each, drawn from real
customer/merchant accounts):

- **shared_device**: `size` accounts tagged with the same synthetic
  `device_id`. Obvious also adds a synchronized payment from every member to
  one shared merchant within a tight step window; subtle is the device tag
  alone, no accompanying transaction pattern.
- **shared_payout**: `size` accounts routed into one new downstream payout
  account. Obvious lands every leg in a 5-step window (fast fan-in); subtle
  spreads legs over a 60-step window, closer to coincidental timing.
- **circular_flow**: an A -> B -> C -> ... -> A transaction cycle. Obvious
  carries the same amount every leg, one step apart (classic layering);
  subtle shrinks the amount slightly each hop and spaces legs 5-20 steps
  apart.

Plus **legit_cluster** hard negatives (6 total): several customers paying
one popular merchant, spread widely over time with no shared device --
superficially the same fan-in shape as shared_payout, but not collusive.
Without these, precision/recall would be measured against an unrealistically
easy problem (see `src/eval/report.md`'s worked false-positive example for
what this looks like on real, unplanted data too).

**Train/test split**: stratified by `(ring_type, difficulty)` so both splits
contain every kind of ring (~30% test per group, with a floor of at least 1
ring). The test split is the only one `eval/metrics.py` scores against --
train exists purely so a threshold like `FLAG_SCORE_FLOOR` could be tuned
without touching held-out data. Every planted node/relationship carries
`ring_id`/`ring_type`/`difficulty`/`split` properties directly in Neo4j (see
`ARCHITECTURE.md` § Phase 1), so this ground truth is queryable, not just
implicit in the Python objects that built it.

## Scale actually used

The results in `README.md`/`src/eval/report.md` were generated from a graph
loaded with `--sample-frac 0.0157` (~100,005 sampled transactions out of the
full 6,362,620): **192,715 account nodes, step range 1-765** (the full
743-step timeline). `--sample-frac`, not `--nrows`, is what gives that full
timeline -- `--nrows` takes PaySim's chronologically-first N rows, which
only spans a handful of steps and silently breaks any time-window-based
detection signal (see `ARCHITECTURE.md` § Phase 1).

## Reproducibility

The CSV isn't included in this repo -- at ~470MB it's well over GitHub's
limits, and it isn't the interesting part of this project anyway (the
planted ground truth is).

1. Download `paysim.csv` from [Kaggle](https://www.kaggle.com/datasets/ealaxi/paysim1)
   (Kaggle account required; use the Kaggle CLI or the website's download
   button).
2. Place it at `archive/paysim.csv` in the repo root.
3. Run the pipeline as in the README's Quickstart -- `uv run python main.py`
   (or, to just load the graph without the rest of the pipeline,
   `uv run python -m src.data.build_graph --sample-frac 0.0157 --wipe`).
   Either way this loads PaySim, plants the synthetic rings described above,
   and pushes everything into Neo4j.

Both the row sample (`random_state=42` in `load_paysim()`) and the ring
planting (`PlantConfig.random_seed = 42`) are seeded, so re-running the same
command against the same downloaded CSV reproduces the same graph and the
same planted rings exactly -- not just the same shapes/counts. A different
`--sample-frac`/`--nrows` value, or `--nrows` instead of `--sample-frac`,
will not.
